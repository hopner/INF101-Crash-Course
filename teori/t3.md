## Konsept

**Polymorfisme** lar oss behandle ulike typer gjennom et felles grensesnitt. En lang if/else-kjede som sjekker type er et typisk anti-mønster — den vokser for hver ny type, og koden som bruker klassen vet for mye om internene. Med polymorfisme kan vi legge til en ny type _uten_ å endre eksisterende kode.

## Oppgave

Se over følgende kode. Den beregner areal og omkrets for ulike former:

```java
public class ShapeCalculator {
    public static double area(String type, double a, double b) {
        if (type.equals("rectangle")) {
            return a * b;
        } else if (type.equals("circle")) {
            return Math.PI * a * a;  // a = radius
        } else if (type.equals("triangle")) {
            return 0.5 * a * b;      // a = base, b = høyde
        }
        throw new IllegalArgumentException("Ukjent type: " + type);
    }

    public static double perimeter(String type, double a, double b) {
        if (type.equals("rectangle")) {
            return 2 * (a + b);
        } else if (type.equals("circle")) {
            return 2 * Math.PI * a;
        } else if (type.equals("triangle")) {
            return a + b + Math.sqrt(a*a + b*b); // forenklet
        }
        throw new IllegalArgumentException("Ukjent type: " + type);
    }
}
```

### a) 3 poeng — Hva er problemet?

Forklar minst to konkrete problemer med denne koden, sett i lys av det vi har lært om god OOP-design.

### b) 4 poeng — Redesign

Beskriv hvordan du ville redesignet koden med **grensesnitt og polymorfisme**. Du trenger ikke skrive full kode — en god forklaring med klassenavn og metoder holder. Hva er fordelene med det nye designet?

### c) 1 poeng — Arv vs. Grensesnitt

Kunne du brukt _arv_ i stedet for grensesnitt her? Hva ville du valgt og hvorfor?

## Fasit

### a) Problemene

- Koden er avhengig av string-verdier og mange `if/else`-sjekker.
- Hver ny form krever at du endrer eksisterende kode i `ShapeCalculator`.
- Klassene som bruker kalkulatoren må kjenne til alle typer og detaljer.
- Koden bryter Open/Closed-prinsippet.

### b) Redesign med grensesnitt og polymorfisme

Lag et grensesnitt som for eksempel heter `Shape`, med metoder som `area()` og `perimeter()`.

Deretter lager du egne klasser som `Rectangle`, `Circle` og `Triangle` som implementerer dette grensesnittet. Hver klasse kjenner sine egne regler for areal og omkrets.

Et annet alternativ er en abstrakt klasse `Shape` med felles felt eller hjelpemetoder, og subklasser for hver konkret form.

**Fordeler:**

- ny type kan legges til uten å endre gammel kode
- mindre if/else og mindre duplisering
- enklere testing av hver form for seg
- tydeligere ansvar per klasse

### c) Arv vs. Grensesnitt

Ja, du kunne brukt arv hvis det fantes en naturlig felles base med delt oppførsel eller delte felt.

Her ville jeg valgt **grensesnitt** som hovedløsning, fordi formene ikke nødvendigvis deler mye implementasjon, men deler en kontrakt. Hvis du har felles kode eller tilstand, kan en abstrakt superklasse kombineres med grensesnitt.
