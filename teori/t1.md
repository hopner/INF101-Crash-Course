## Konsept

**Encapsulation** handler om å beskytte objektets interne tilstand. Det handler ikke bare om å skrive `private` foran felter, men om å sikre at objektet _alltid_ er i en gyldig tilstand, uansett hva brukeren av klassen prøver å gjøre. Tre lag: (1) private felter, (2) validering i muterende metoder, (3) ikke lekke mutable objekter ut.

## Oppgave

Se over følgende klasse. Det er bevisst lagt inn **tre encapsulation-feil**.

```java
public class BankAccount {
    public double balance;                        // (1)
    private List<String> transactionHistory;

    public BankAccount(double initialBalance) {
        this.balance = initialBalance;             // (2)
        transactionHistory = new ArrayList<>();
    }

    public void deposit(double amount) {
        balance += amount;                         // (3)
        transactionHistory.add("+ " + amount);
    }

    public void withdraw(double amount) {
        balance -= amount;                         // (4)
        transactionHistory.add("- " + amount);
    }

    public List<String> getHistory() {
        return transactionHistory;                 // (5)
    }
}
```

### a) 4 poeng — Finn feilene

Identifiser de tre encapsulation-feilene. Forklar kort hva som kan gå galt i hvert tilfelle.

### b) 4 poeng — Skriv tester

Skriv JUnit5-tester (du kan ikke kjøre dem, fokuser på innhold og logikk) som **avslører** minst to av de tre feilene. En test som passerer med koden over, men feiler med den rettede koden, er ikke god nok — det skal være omvendt.

### c) 2 poeng — Rett opp

Beskriv kort hva du ville endret for å fikse alle tre feilene.

## Fasit

**a) De tre feilene:**

1. `balance` er `public` → hvem som helst kan skrive `account.balance = -9999` utenfra.
2. Ingen validering i konstruktøren → `new BankAccount(-500)` lager konto med negativ saldo.
3. `deposit` og `withdraw` validerer ikke amount → negativt beløp i deposit, uttak som overskrider saldo, er alle mulig.
4. `getHistory()` returnerer den faktiske listen → bruker kan gjøre `account.getHistory().clear()` og slette historikken.

**b) Tester som avslører feil:**

```java
// Avslører feil 2 (negativ initial saldo)
@Test
void shouldRejectNegativeInitialBalance() {
    assertThrows(IllegalArgumentException.class,
        () -> new BankAccount(-100));
}

// Avslører feil 3 (overtrekk)
@Test
void shouldRejectWithdrawalExceedingBalance() {
    BankAccount acc = new BankAccount(100);
    assertThrows(IllegalArgumentException.class,
        () -> acc.withdraw(200));
}

// Avslører feil 4 (lekkasje av liste)
@Test
void historyShouldBeImmutable() {
    BankAccount acc = new BankAccount(100);
    acc.deposit(50);
    acc.getHistory().clear();
    assertEquals(1, acc.getHistory().size()); // feiler med feil kode
}
```

**c) Rettinger:**

- Gjør `balance` `private`.
- Valider i konstruktøren: `if (initialBalance < 0) throw ...`
- Valider i `deposit`/`withdraw`: sjekk at amount > 0 og at saldo ikke går under 0.
- Returner kopi i `getHistory()`: `return new ArrayList<>(transactionHistory)` eller `List.copyOf(...)`.
